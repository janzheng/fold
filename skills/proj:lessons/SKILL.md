# Lessons and gotchas

Find the project's existing `GOTCHAS.md`, `lessons.md`, runbook, or equivalent.
Use that location; otherwise start `GOTCHAS.md` at the relevant project root.
Do not create parallel lessons and gotchas stores for the same purpose.

## Consult

Search by symptom, component, or operation before repeating known-tricky work.
Read matching entries and linked evidence; check whether the advice still
applies. Prefer a current verified remedy to a superseded prescription.
Do not load the entire ledger when a targeted lookup suffices.

## Capture

Capture an observed reusable trap, not every failed attempt or hypothetical risk.
Check for an existing entry first; add evidence to it instead of duplicating.
Use a stable ID following the existing numbering, or append the next number.

Each entry needs a symptom-shaped title, date, cause (or explicitly unknown),
remedy/prevention, applicability, and an evidence link. Distinguish a workaround
from a fixed root cause. A cause hypothesis is not an established fact.

Keep entries concise. Link the run log or lab note for the history. When advice
changes, mark fixed, superseded, or obsolete with the date and evidence; retain
the original reasoning and stable ID. Do not renumber or silently delete.

For longer debugging ledgers and indexes, read `proj:audit`'s `gotchas.md`
reference when available. A lesson does not need a separate pitfall document
unless the project already uses that distinction.

Report the entry location and the behavior that should change next time.
